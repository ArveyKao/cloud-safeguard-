# Cloud Safeguard 产品说明（v0.1）

> **给 AI agent 能力，而不是长期凭据。**
> Capabilities, not credentials.

- 版本：`v0.1.0`（MVP，本地可运行的自托管制品）
- 形态：单个 Go 二进制 + 内嵌 Web 控制台 + `csg` CLI；单租户；阿里云
- 状态说明：本文描述**已冻结的产品规格**与 v0.1 已交付范围；路线图条目均明确标注
  **Roadmap**，不属于 v0.1。规格原文见 [SPEC.md](SPEC.md)，规范契约见
  [CONTRACT.md](CONTRACT.md)。

## 1. 真实痛点

这不是虚构的需求。它来自一个真实的搭建过程：让 AI agent 管理一个真实的阿里云账号
（ECS、域名解析、nginx、Let's Encrypt 证书），最自然的做法是把一个长期有效的 RAM
AccessKey 交给 agent。能跑通之后，问题才开始暴露：

### 1.1 长期 AK/SK 会被复制到每一个角落

同一个 broker AccessKey 实际上出现在：

- 服务器的 `~/.aliyun/config.json`（阿里云 CLI 的 profile）；
- 服务器的 `~/.acme.sh/account.conf`（Let's Encrypt DNS-01 自动续签的凭据）；
- agent 自己的工具/插件配置；
- 可能还有 CI secrets、脚本、shell history、聊天记录。

**轮换一次 key，等于把上述所有副本逐个找出来改一遍。** 漏掉一处不会立刻报错，而是
在几个月后证书静默续签失败、任务突然挂掉——那时已经没人记得原因。

### 1.2 方便和最小权限只能二选一

- 想要"不用每次折腾权限"，最省事的答案是 `AdministratorAccess`；
- 但一条被泄漏的长期 key（agent 日志、粘贴的对话、被入侵的机器）就是
  **整个云账号被接管**——ECS、DNS、账单、数据全在其中；
- 想真正最小权限，就要为每个任务建 RAM 用户/策略，走控制台、等生效、试错、再改。
  摩擦高到所有人最终都退回了全权限。

### 1.3 审计无法归因到 agent / 任务 / 授权

云厂商原生审计（ActionTrail）只能告诉你"**某个 RAM 用户**做了什么"。它无法回答：

- 是哪个 agent 做的？
- 属于哪个任务？
- 是谁批准的？批准时的理由和 TTL 是什么？
- 这次操作对应的是哪一次能力授权？

出问题时，这是取证和合规上最关键的几个问题——而现有工具答不出来。

### 1.4 "每条命令都人工审批"不是解法

把 agent 的每条命令都弹给人审批，安全是安全了，但 agent 退化成"聊天式 shell"：
人成了瓶颈，agent 的价值（自动化、连续执行、无人值守）也消失了。人不可能一天审批
几百条 `describe-instances`。

### 1.5 根本矛盾

> **方便（convenience）× 最小权限（least privilege）× 可追责（accountability）**，
> 现有做法最多只能三选二。

Cloud Safeguard 的产品命题：**三者可以同时成立**，前提是把"凭据"从 agent 手里拿走，
换成**能力**。

## 2. 平台是什么

**Cloud Safeguard 是位于 AI agent 和云账号之间的自托管控制平面**——非人类云访问的
授权层（authority layer）。

它做四件事：

1. **收口长期凭据**：云账号的 broker AccessKey 只存在控制平面的 AES-256-GCM
   加密保险库（vault）里，永不通过 API 返回、永不写日志。它只在一个瞬间被解密：
   为某个 lease 铸造短时凭据。
2. **把权限变成能力租约（capability lease）**：agent 请求的不是"密钥"，而是
   「某个命名能力 + 具体资源参数 + 时长 + 理由」。策略引擎立即给出可解释的决定：
   自动批准 / 等待人工批准 / 拒绝。
3. **即时铸造最小权限凭据（JIT STS）**：批准后，控制平面把能力模板渲染成一份
   内联 IAM 策略（如仅限 `acs:alidns:*:*:domain/arveykao.com`），调用阿里云 STS
   `AssumeRole`，得到一个短时、按需、带会话名（`csg-<agent>-<lease>`）的临时凭据。
4. **全程留痕、到期即死、可撤销**：TTL 上限 + 后台 sweeper + 撤销 + 哈希链审计；
   每条请求、每次批准、每次凭据发放、每次云端调用都能归因到 agent + lease。

一句话：**agent 永远拿不到长期云凭据；它拿到的是"某件事、做多久、被谁批准"的能力。**

## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| **Provider（云账号）** | 接入的一个云账号：一份加密保存的 broker AccessKey + 一个 RAM role。模式：`sts`（真实云）/ `mock`（内置演示云）。 |
| **Capability（能力）** | 命名的、最小权限的权限包：风险等级、参数化 IAM 策略模板、默认/最大 TTL。例如 `aliyun.dns.manage` 限定一个域名。 |
| **Agent（智能体身份）** | 非人类身份：一次性展示的 bearer token、被授予的能力集合、单 agent 的 TTL/并发/速率限制。 |
| **Lease（租约）** | 平台的中心对象：某 agent 对某能力、某参数、某时长的请求 + 理由。策略引擎给出 auto-approve / require-approval / deny；活跃 lease 持有一份加密的短时凭据。 |
| **Approval（审批）** | 人对 pending lease 的决定：批准（可调 TTL、带备注）或拒绝（必须写理由）。 |
| **Vault（保险库）** | AES-256-GCM 信封加密：broker AccessKey 和 lease 凭据只以密文形式落库，主密钥存放在数据库之外。 |
| **Audit event（审计事件）** | 只追加、哈希链保护的记录：所有安全相关动作，包括每一次 mock 云 API 调用。 |

内置能力目录（v0.1，共 5 个，风险从低到高）：

| 能力 ID | 用途 | 风险 | 默认/最大 TTL |
| --- | --- | --- | --- |
| `aliyun.cloud.read` | 只读资源盘点（ECS/DNS/OSS 的 Describe/List） | low | 900s / 1800s |
| `aliyun.dns.manage` | 管理单个域名的解析记录 | medium | 900s / 1800s |
| `aliyun.cert.dns01` | 单个域名的 ACME DNS-01 challenge 记录 | medium | 600s / 1200s |
| `aliyun.ecs.instance.ops` | 启停/重启单台 ECS 实例 | high | 900s / 1800s |
| `aliyun.iam.break_glass` | 紧急全账号权限（break-glass） | critical | 900s / 1800s |

## 4. 核心工作流

### 4.1 低风险只读：零人工、2 秒内

1. agent 用**自己的平台 token**（`csg_agt_...`，不是云 key）请求
   `aliyun.cloud.read`，带理由。
2. 策略引擎按顺序检查：能力已授予 → 能力已启用 → provider 可用/活跃 → 理由 →
   TTL 在上限内 → 并发/速率未超 → 风险 ≤ 自动批准阈值 → **auto_approve**。
3. 控制平面解密 broker key、渲染只读策略、调用 STS、加密保存凭据 → lease `active`。
4. agent 拉取短时凭据（每次拉取都有审计），直接用于现有阿里云 CLI/SDK。
5. 到期后 sweeper 自动清理；agent 也可以主动 revoke。

### 4.2 高风险变更：一次点击审批、30 秒内

1. agent 请求 `aliyun.dns.manage`，参数 `domain=arveykao.com`，TTL 10 分钟，理由
   "为证书续签添加 ACME TXT 记录"。
2. 策略引擎返回 **require_approval**，lease 进入 `pending`，**还没有任何凭据**。
3. 操作者在控制台（或 CLI）看到风险、参数、理由、请求 TTL，一键批准，可改短 TTL、
   写备注。服务端重新校验上限后才铸造凭据。
4. agent 继续执行；它拿到的凭据只能操作**这一个域名**——同一凭据去重启 ECS 会被
   `403 Forbidden.RAM`。

### 4.3 拒绝、过期、撤销

- **拒绝**：agent 未被授予某能力 → 立即 `denied`，给出具体规则原因（例如
  `capability_not_granted`），不可能拿到凭据；管理员也可以拒绝 pending 请求并写理由。
- **过期**：pending 超过等待窗口 → 自动过期；active 超过 TTL → 过期并擦除平台侧
  密文。
- **撤销**：任意时刻按 agent 或按 lease 撤销；mock 模式下下一次云端调用立即 401；
  真实 STS 模式的下一次续租被拒绝（已签发的 STS 凭据无法被云厂商单条即时吊销，
  这是已记录的残留风险，见 [SECURITY.md](SECURITY.md)）。
- **Break-glass**：critical 能力必须显式 `break_glass=true` 且必须人工批准，审计以
  critical 级别记录；演示中包含"批准 → 使用 → 撤销 → 原 token 立即失效"。

### 4.4 轮换：一处操作、零 agent 改动

操作者在控制台点一次（或 `csg providers rotate`）：用新 AK/SK 重新加密写入 vault，
审计记录（只含掩码后的 AK ID）。现有 lease 的凭据不受影响；下一个 lease 用新凭据
铸造；agent、服务器脚本、cron 全部不需要改。这正是过去"翻遍所有副本"场景的反面。

## 5. 和现有方案比，差在哪

| 方案 | 方便 | 最小权限 | 审计/撤销 | 结论 |
| --- | --- | --- | --- | --- |
| **全权限长期 AK 直接给 agent** | 高 | 无 | 只有云厂商层面、无法归因到 agent | 快，直到出事；爆炸半径 = 整个账号 |
| **每个任务建一个 RAM 用户 + 策略** | 低（每次都要控制台/API 折腾） | 好 | 归因弱、轮换更分散 | 摩擦会把人推回全权限 |
| **每条命令都人工审批** | 极低 | 好 | 聊天记录 | agent 失去价值，人变成瓶颈 |
| **每条能力都快照一张"临时 STS 凭据"**（Cloud Safeguard） | 高（低风险零人工） | 好（按 lease 渲染的内联策略） | 强（按 agent/lease 归因、哈希链、可撤销） | 三者同时成立 |

关键差别不是"有没有凭据"，而是**凭据的粒度与生命周期**：

- 粒度：从"整个账号"变成"一个能力 + 一个资源参数 + 一段 TTL"；
- 生命周期：从"永久直到手动轮换"变成"分钟级自动过期"；
- 归属：从"某个 RAM 用户"变成"某个 agent 的某次 lease、某个人批准"。

## 6. 价值主张与成功指标

### 价值主张

- **对使用者（工程师/运维）**：把 agent 接上真实云账号时，不再需要交出长期全权限
  key；不再需要为每个新任务做 RAM 权限体操；轮换从"翻遍所有副本"变成"点一次"。
- **对 agent**：拿到的是现成的环境变量（`ALIBABA_CLOUD_ACCESS_KEY_ID` /
  `..._SECRET` / `..._SECURITY_TOKEN`），现有阿里云 CLI、Terraform、SDK 直接可用，
  不需要改工具链。
- **对组织**：每个非人类动作都有主体、理由、授权人和完整时间线；爆炸半径被 TTL 和
  内联策略压缩到最小；事故响应有确定的撤销路径。

### 成功指标（v0.1 验收标准）

| 指标 | 目标 |
| --- | --- |
| 只读 access 的 time-to-credential | < 2 秒，零人工 |
| 受控写操作的 time-to-credential（含人工批准） | < 30 秒 |
| 操作者轮换凭据 | 一次命令/控制台操作，零 agent 改动 |
| vault 之外的长期云凭据 | 0 |
| lease 请求与云端 API 调用的审计归因率 | 100% |
| 安全性验证 | 越权动作 403、伪造/过期/被撤销凭据 401、篡改审计链可检出 |

## 7. 非目标与边界（v0.1）

明确**不做**以下事情，避免过度承诺：

- **多租户 / SaaS / 用户账号体系 / SSO / 人类 RBAC**：v0.1 只有一个管理员 token。
- **阿里云之外的云厂商**：`provider` 抽象已预留，但 v0.1 只实现阿里云。
- **免凭据代理模式（credential-free proxy）**：v0.1 仍把短时 STS 凭据交给 agent，
  这是刻意的权衡（兼容现有工具链）；"agent 永远不见云凭据"是 P1 方向。
- **按参数约束授权**：v0.1 中一个被授予 `aliyun.dns.manage` 的 agent 可以传任意合法
  域名参数；把授权钉死到具体资源（`grant.params`）是 P1。
- **HA / Kubernetes / 外部数据库 / 外部 KMS/HSM**：单进程 + SQLite + 本地主密钥。
- **对话式审批（Slack/Feishu）**：v0.1 只有 CLI 与控制台审批；通知/审批接入是 P2。
- **计费、许可证、市场**：没有商业功能代码。

另有已记录的**残留风险**（不是"不支持"，而是"确实无法完全消除，需要运营配合"）：

- 真实云 STS 无法对单条会话做即时吊销；撤销后的兜底是拒绝续租 + 轮换 RAM role
  策略（已签发凭据最长存活到自己的 TTL）。
- 审计哈希链是**防篡改可检出**，不是**防篡改写入**：能整库重写的人可以重算整条链。
- `mock` 模式是演示/测试设施，**不是安全边界**。
- 主密钥保护"静态密文"；主密钥与数据库同时泄漏时，vault 内容可被解密。
- 没有经过独立第三方安全审计；`sts` 模式在本构建中只用假 STS 端点做过单元测试，
  未在真实账号上运行过。

细节、缓解措施与部署加固清单见 [SECURITY.md](SECURITY.md)。

## 8. 路线图（Roadmap，不属于 v0.1）

- **P1 — 把爆炸半径再压一个数量级**
  - **免凭据代理模式**：agent 只与 `csg` 通信，由 `csg` 注入 broker 凭据转发云 API
    请求；agent 永远看不到任何云凭据。这是安全上更强的终态。
  - **按参数授权**：grant 层面约束 `domain` / `instance_id` 等参数，进一步收紧
    "agent 有该能力但只能操作特定资源"。
- **P2 — 从单机工具变成团队基础设施**
  - 对话式审批（Slack / Feishu / 邮件）与审批 Webhook；
  - SSO / 人类 RBAC / 多租户隔离；
  - 多云端 provider（AWS / GCP / 腾讯云等）；
  - 外部 KMS / HashiCorp Vault / HSM 托管主密钥；SIEM 审计导出；
  - Kubernetes / Helm 部署与 HA（外部数据库）。

路线图条目的原则：只有在 v0.1 的核心安全属性（凭据收口、最小权限、归因、可撤销）
被证明可用之后，才扩展规模与形态。

## 9. 商业模式思考（简要、诚实）

v0.1 是一个技术验证，不构成商业模式结论。可参考的开源基础设施路径：

- **开源核心（Open-source core）**：控制平面、CLI、内置能力目录、审计链做成开源
  项目（许可证待定），降低采用门槛，接受社区审计——安全产品尤其需要"可检查"。
- **托管版（Hosted）**：把 vault、审计存储、审批通知、策略合规模板做成托管服务，
  按 agent/lease 数或用云账号数订阅；适合不想自建高可用控制面的小团队。
- **企业版（Enterprise）**：SSO/RBAC、多租户、外部 KMS、SIEM 导出、审计留存与
  合规报告、SLA 支持；核心价值是"审计与治理"，而不是"代管 key"。
- **能力市场（长期）**：可组合、可审计的能力包/策略模板（例如"只允许某域名的
  ACME 续签"），可能形成生态，但这是远期假设，不是当前重点。

产品立场：**安全属性必须可验证、可自托管**。托管版卖的是便利和治理，不是把长期
凭据交给第三方；这也是"capabilities, not credentials"在商业模式上的延伸。

## 10. 诚实说明

- v0.1 是本地可运行制品（单机、单进程、SQLite），不是生产级服务：
  没有高可用、没有正式的安全审计、没有多用户。
- 自动化验收与演示完全跑在 `mock` 云上，不需要真实云账号；README/QUICKSTART 里
  真实 `sts` 模式的命令**未经真实账号执行**，须自行在账号中验证。
- 产品解决的是**"agent 怎么安全地获得云权限"**；它不解决密钥管理基础设施本身
  （KMS/HSM）、不解决 agent 主机被入侵后眼前的 STS 凭据、也不解决"agent 被合法
  授权后滥用参数"这类问题——这些在 [SECURITY.md](SECURITY.md) 中有逐项说明。
